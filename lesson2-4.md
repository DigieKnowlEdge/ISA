# Threat Modeling AI Solutions

---

## Lesson Objectives

* Identify key differences between AI and traditional IT systems from a threat modeling perspective
* Apply STRIDE to AI solution components
* Understand the OWASP Top 10 for Large Language Models (LLMs)
* Know the Dos and Don'ts when threat modeling AI solutions

---

## Why AI Is Different

Traditional IT systems have **deterministic, auditable logic**

AI systems introduce:

* Non-deterministic outputs
* Opaque decision-making ("black box")
* New attack surfaces: training data, model weights, prompts
* Emergent behaviors that are hard to predict
* Third-party model dependencies (supply chain)

---

## AI System Components to Model

Before applying STRIDE — know what you are modeling:

| Component | Examples |
|---|---|
| Training pipeline | Data sources, labeling, fine-tuning |
| Model / weights | LLM, classifier, embeddings |
| Inference API | REST endpoint, SDK call |
| Prompt / context | System prompt, user input, RAG context |
| Plugin / tool layer | Function calling, agents, external APIs |
| Output consumers | UI, downstream systems, automated actions |

---

## Applying STRIDE to AI

You already know STRIDE — now map it to the AI domain:

| Threat | AI-specific concern |
|---|---|
| **S**poofing | Impersonating a trusted model or user identity |
| **T**ampering | Poisoning training data or model weights |
| **R**epudiation | AI denying or misattributing decisions |
| **I**nformation Disclosure | Leaking training data or system prompts |
| **D**enial of Service | Flooding inference, resource exhaustion via prompts |
| **E**levation of Privilege | Prompt injection to bypass restrictions |

---

## STRIDE: Spoofing & Tampering in AI

**Spoofing**
* Attacker impersonates a trusted model endpoint
* Fake embeddings returned to RAG pipeline
* Jailbroken model poses as a "safe" system

**Tampering**
* Data poisoning: inject malicious samples into training set
* Fine-tuning backdoors ("sleeper" triggers)
* Adversarial perturbations to model inputs at inference

---

## STRIDE: Information Disclosure & DoS in AI

**Information Disclosure**
* Training data memorization → PII extraction
* System prompt exfiltration via crafted user prompts
* Model inversion attacks to reconstruct training data

**Denial of Service**
* Computationally expensive prompts (token flooding)
* Repeated inference calls to exhaust quota
* Adversarial inputs causing repeated retries or errors

---

## STRIDE: Repudiation & EoP in AI

**Repudiation**
* No log of which model version answered which query
* AI output hard to attribute for accountability
* Audit gaps in agentic / autonomous pipelines

**Elevation of Privilege**
* Prompt injection: user overrides system prompt restrictions
* Tool/plugin abuse: LLM tricked into calling privileged APIs
* Indirect injection from documents, emails, web pages fed to LLM

# OWASP Top 10 for LLMs

---

## LLM01 – Prompt Injection

**What:** Attacker crafts input that overrides the system prompt or hijacks model behavior

* **Direct injection:** User input contradicts or replaces instructions
* **Indirect injection:** Malicious content in external data (emails, docs, web) fed to LLM

**Impact:** Data exfiltration, unauthorized actions, safety bypass

**Countermeasure:** Treat all external content as untrusted data, not instructions

---

## LLM02 – Insecure Output Handling

**What:** LLM output is passed to downstream systems without validation

* SQL queries generated by LLM → SQL injection
* HTML generated by LLM → XSS
* Shell commands generated by LLM → RCE

**Impact:** Classic injection attacks through AI-generated content

**Countermeasure:** Validate and sanitize LLM output like any user input

---

## LLM03 – Training Data Poisoning

**What:** Attacker corrupts training or fine-tuning data to influence model behavior

* Insert backdoors triggered by specific inputs
* Degrade model quality in targeted areas
* Bias the model toward attacker-desired outputs

**Impact:** Persistent, hard-to-detect compromise of model behavior

**Countermeasure:** Data provenance, integrity checks, anomaly detection on training data

---

## LLM04 – Model Denial of Service

**What:** Attacker causes resource exhaustion through crafted inputs

* Recursive or deeply nested prompts
* Context window flooding
* Repeated high-cost inference requests

**Impact:** Service unavailability, high cloud costs

**Countermeasure:** Rate limiting, token limits per request, cost monitoring

---

## LLM05 – Supply Chain Vulnerabilities

**What:** Risks from third-party models, datasets, plugins, or infrastructure

* Malicious or backdoored pre-trained model
* Compromised model hosting / hub
* Vulnerable dependencies in ML frameworks

**Impact:** Hard to detect, wide blast radius

**Countermeasure:** Verify model provenance, sign and pin dependencies, monitor for compromise

---

## LLM06 – Sensitive Information Disclosure

**What:** LLM reveals confidential data from training data or runtime context

* Memorized PII, credentials, or IP from training corpus
* System prompt leaked to user via crafted query
* RAG retrieval exposing documents the user should not see

**Impact:** Privacy violation, credential leakage, IP exposure

**Countermeasure:** Data minimization, prompt hardening, output filtering, access control on RAG

---

## LLM07 – Insecure Plugin Design

**What:** Plugins and tools that extend LLM capabilities introduce new attack surface

* Overly broad permissions granted to plugins
* No validation of plugin inputs / outputs
* LLM autonomously calls privileged plugins based on attacker-controlled input

**Impact:** Unauthorized actions, lateral movement via AI agent

**Countermeasure:** Least privilege for plugins, human-in-the-loop for sensitive actions

---

## LLM08 – Excessive Agency

**What:** LLM is given too much autonomy to act on the real world

* Autonomous email sending, file deletion, API calls
* No human confirmation for high-impact actions
* Scope of agent actions not bounded

**Impact:** Unintended or malicious real-world consequences

**Countermeasure:** Define and enforce agent action boundaries, require human approval for impactful operations

---

## LLM09 – Overreliance

**What:** Users or systems blindly trust LLM output without verification

* Hallucinated facts accepted as truth
* Security controls bypassed based on AI recommendation
* Compliance or legal advice acted on without review

**Impact:** Incorrect decisions, missed vulnerabilities, liability

**Countermeasure:** Human review for high-stakes decisions, cite sources, communicate confidence levels

---

## LLM10 – Model Theft

**What:** Unauthorized extraction or replication of a proprietary model

* Model API queried repeatedly to clone behavior (model extraction)
* Model weights stolen from storage or MLOps pipeline
* Knowledge distillation attacks via systematic prompting

**Impact:** IP loss, competitive harm, stolen safety alignment

**Countermeasure:** Rate limiting, query monitoring, access controls on weights, watermarking

---

# Key Differences vs. Traditional IT

---

## New Attack Surfaces (1/2)

Traditional TM covers: network, application, data store, external entity

AI adds unique surfaces:

| New Surface | Threat |
|---|---|
| Training data | Poisoning, bias injection |
| Model weights | Theft, backdoor, integrity |
| System prompt | Exfiltration, injection |
| Context / RAG | Indirect injection, over-retrieval |

---

## New Attack Surfaces (2/2)

| New Surface | Threat |
|---|---|
| Plugin / tool calls | Privilege abuse, insecure design |
| Agentic loops | Cascading actions, loss of control |
| Third-party model | Supply chain, black-box behavior |
| Feedback / RLHF data | User-driven poisoning over time |

---

## What Does Not Change

Traditional controls still apply — AI does not replace them:

* Authentication & authorization for the API
* Transport security (TLS)
* Input validation on the API boundary
* Logging and monitoring
* Secrets management (API keys for LLM providers)
* Network segmentation for MLOps infrastructure

---

## Non-Determinism: A Threat Modeling Challenge

AI outputs are **probabilistic** — same input ≠ same output

Implications for threat modeling:

* Harder to define "expected behavior" for trust boundaries
* Security testing requires statistical coverage, not just test cases
* Attacker can iterate prompts — one rejection is not a defense
* Behavioral changes after model updates are unpredictable

**Principle:** Defense must be systematic, not prompt-by-prompt

# Dos and Don'ts

---

## Dos (1/2)

* **Do** model the full pipeline: data → training → inference → output → consumer
* **Do** treat all external content fed to LLM as untrusted input
* **Do** apply least privilege to every plugin and tool the LLM can call
* **Do** require human-in-the-loop for any irreversible or high-impact action
* **Do** include the model version and prompt version in your threat model

---

## Dos (2/2)

* **Do** check data provenance for training and fine-tuning data
* **Do** log prompts and completions for audit and incident response
* **Do** define the trust boundary around the system prompt explicitly
* **Do** validate and sanitize LLM output before passing it to downstream systems
* **Do** run the OWASP LLM Top 10 as a checklist alongside STRIDE

---

## Don'ts (1/2)

* **Don't** assume prompt-level guardrails are sufficient security controls
* **Don't** expose the system prompt or internal context to users
* **Don't** grant LLM agents permissions beyond what is needed for the use case
* **Don't** treat AI-generated code or queries as trusted output without review
* **Don't** skip threat modeling because "the model handles it"

---

## Don'ts (2/2)

* **Don't** rely on the model provider's safety filters as your only defense
* **Don't** feed sensitive data into third-party LLMs without data classification
* **Don't** deploy agentic systems without defining and enforcing action boundaries
* **Don't** assume a rejection means the system is secure — attackers iterate
* **Don't** forget the classic supply chain: ML frameworks, libraries, model hubs

---

## Threat Modeling Checklist for AI

Quick reference — did you cover:

- [ ] Training data integrity and provenance
- [ ] Model weight protection and versioning
- [ ] System prompt confidentiality and injection
- [ ] Input validation on all LLM API boundaries
- [ ] Output sanitization before downstream use
- [ ] Plugin / tool least privilege
- [ ] Agent action scope and human approval gates
- [ ] Logging of prompts and completions
- [ ] Third-party model and library supply chain
- [ ] Non-determinism in security testing approach

---

## Summary

* AI systems introduce **new attack surfaces** on top of classical ones — apply STRIDE to all of them
* **Prompt injection** is the AI equivalent of SQL injection — treat it with the same seriousness
* OWASP Top 10 LLM is your domain-specific threat catalogue
* The biggest gap vs. traditional TM: **non-determinism**, **supply chain depth**, and **agentic autonomy**
* Core principle: **assume the model is untrusted** — validate inputs, validate outputs, enforce least privilege
